# 100 章规模演练(2026-11-14,桩模型)

## 为什么用桩

真实模型每章要走 4 次调用(场景规划 → 场景写作 → 摘要 → 实体 → 认知),100 章约 400 次,
按本机网关实测每章 20–90 秒,需要 3–4 小时,且中途任何一次认知依据校验失败都会停住。
本项要回答的是**编排层**问题(丢章、断点恢复、终态、耗时),这些与文本是否文学无关,
所以用本地确定性桩替换模型,把变量收干净。

> **桩文本不是小说,不能当质量证据。** 因此本目录只保留元数据与一份桩样例,
> `continuity.json` 里的 `repeated_opening`(99 次)与 `book_fact_missing`(3 次)是
> 桩内容本身造成的,不代表任何生成质量结论。

```bash
cd backend
python -m scripts.quality_eval.continuity_probe \
  --database-url postgresql+asyncpg://postgres:postgres@127.0.0.1:55432/aiwrite_eval \
  --out ../docs/evaluation/continuity-20261114-scale100 \
  --chapters 100 --stub-model --resume --max-consecutive-errors 3
```

## 演练过程

1. **首轮**:100 章从头跑,跑到 **第 34 章时被 SIGKILL**(模拟进程被强杀)。
   此刻磁盘上有 34 个 `chNN.txt`,但第 34 章的落库与提取还没提交。
2. **恢复**:带 `--resume` 重跑。

## 结果

| 指标 | 值 |
|---|---|
| 记录条数 | 100(逐章都有终态记录,无缺失编号) |
| 状态分布 | `ok` 67 / `resumed` 33 / `error` **0** |
| 实体提取 | 67/67 生成章 `status: ok, reason: projected` |
| 认知提取 | 67/67 `completed` |
| 摘要 | 67/67 已写入 |
| 生成阶段累计耗时 | **14.2 秒**(桩,中位 0.2 秒/章) |
| 残稿处理 | 1 份 `ch34.incomplete.txt`,标出并重做 |

`chapters.json` 是逐章台账,`ids.json` 是隔离项目标识,桩样例见 `stub-sample-ch01.txt`。

## 这轮演练暴露的两个工具缺陷(都已修)

### 1. `--resume` 曾按"文件存在"判断完成,留下一个洞

第一次恢复时,第 35 章起全部报:

```
RequiredContextUnavailable: character_cognition_not_ready
```

原因:第 34 章在"正文写完文件、落库尚未提交"的窗口里被杀,磁盘上有 txt 但数据库里
没有 completed 正文、也没有认知记录。旧逻辑只看文件就把这一章跳过去了,于是后续章节
的前置条件永远不成立。

修法:恢复判定改为查数据库 —— 正文已落库且 `status='completed'`,**并且**该章的
`ChapterCognition` 也是 `completed`,才算这一章真做完;否则把残缺文件改名
`chNN.incomplete.txt` 并重做。修完再跑,第 34 章被识别并重做,1→100 全部走完。

这条对生产也有意义:任何"以产物文件是否存在判断任务完成"的恢复逻辑都会在
"写完但没提交"的窗口里留洞。

### 2. `--chapters N` 实际只建了 10 章

手写的章节大纲只有 10 条,`CHAPTERS[:chapters]` 于是永远最多 10 章。规模演练需要更多章,
所以加了 `_chapter_specs()`:超过 10 章的部分沿用同一套设定续写,标题与要求带上章号。
真实模型的 10 章验收不受影响(仍用手写大纲)。

## 这轮**证明**了什么 / 没证明什么

证明:
- 编排层在 100 章量级下不会丢章、不会静默跳过、每章都有明确终态;
- 进程被强杀后能识别"半成品"并重做,完成后 1→100 连续无缺号;
- 实体投影与认知记录在每章都得到终态,前置条件链是连续的。

没证明:
- **文学质量**无关(桩文本);
- 真实模型在 100 章量级的表现(本轮没有跑),包括费用、时延与失败率;
- 并发与多 worker(本轮单进程串行);
- 位置、时间、知情边界的跨章一致性(检查器没有这些能力,见上一份 REVIEW)。
