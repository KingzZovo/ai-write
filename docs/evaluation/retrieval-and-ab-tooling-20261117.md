## 1. 结构感知切块(`chapter_chunker`)

改前:把段落按字数贪心装桶(目标 500、上限 800),空行先被丢掉,于是
**一场戏的结尾和下一场戏的开头会被粘在同一个片段里**,而一段 8 轮的对话会被
从中间切开。

改后(仍不改变对外契约:函数签名、`CHUNK_TARGET_CHARS`/`CHUNK_MAX_CHARS` 默认值、
`md5("{volume_id}_{chapter_idx}_{seq}")` 的 point id 全部不变):

| 规则 | 行为 |
|---|---|
| 对白不切断 | 连续的引号开头段落视为一个"对白往来单元",整段粘在一起,上限 `max_chars × 1.2 = 960` |
| 段落 vs 分场 | **单个空行只是段落分隔**(中文网文常态),不算分场;**两个以上连续空行**才算作者标出的分场 |
| 场景标记 | 段落以 `次日/翌日/第二天/隔日/当晚/当天夜里/与此同时/另一边/另一头/画面一转` 开头时强制开新片段 |
| 超长段落 | 仍按句末标点切;单句超长才硬切 |
| 上限 | 任何片段都不超过 960 字(对白单元自身也受此限) |

### 1.1 我先做错了一版,被真实语料抓出来

第一版把**单个空行**当分场、并把 `——` 也当场景标记。单元测试(合成文本用单换行)
全绿,但在 100 章真实正文上立刻暴露:

| 指标 | 旧算法 | 第一版(错) | 修正后 |
|---|---|---|---|
| 片段数 | 230 | **1109** | 231 |
| 平均片段字数 | 485 | ~90 | 486 |
| 跨场景粘连片段 | 4 | 54 | 4 |
| 对白被切断处 | 4 | **37** | 3 |

原因:真实稿件是"每段之间一个空行",于是每一段都变成独立片段;`——` 又常见于打断语,
把对白切得更碎。修正后回到与旧算法同量级,并且把"单空行不得当分场""`——` 不是分场标记"
写成了两条回归测试。

### 1.2 修正后的真实效果(诚实版)

- 在 100 章、约 1000 字/章的语料上:**片段数 230 → 231、粘连 4 → 4、对白切断 4 → 3**,
  基本等价 —— 这类短章里场景标记很少落在片段中间。
- 在 3,521 字的长章上(一场戏 + 8 轮对话 + 双空行分场 + 场景标记):旧算法把"次日清晨"
  粘在上一个片段里(**粘连 1**),新算法 **粘连 0**。
- 结论:这个改动的价值随章节变长而上升;对短章几乎是中性的。它换来的主要不是"更少片段",
  而是**片段边界与叙事边界对齐**(不会把下一场戏的开头挂在本场末尾)。

19 项离线测试(`tests/test_chapter_chunker_structure.py`,含两条针对上述回归的用例)
+ 引用该模块的 5 个既有文件 24 项回归。

**已知误判**(代价是片段偏大,不会丢字):纯按"首字符是引号"判定对白,
`"活该。"林岚说。` 这类叙述也可能被当对白,最多把片段撑到 960。

## 2. 切块升级会静默清空召回 —— 已修

`vector_provenance.filter_current_memory(chunks=True)` 是【原文回读】的唯一把关点,
它原先要求 `payload["text"] == 重新切块后的 parts[payload["chunk_seq"]]`。
切块算法一变,所有既有 point 都对不上 → **整本书的原文召回被静默过滤干净**
(与"换嵌入模型导致召回 0 点"是同一类事故,我们已经踩过一次)。

现在的判定(`_chunk_vector_matches`,已抽成可单测函数):

1. 章节正文 sha256 必须与 point 记录一致 —— **改过稿的旧点仍然失败**,引文可信度不降;
2. seq+文本完全一致 → 有效(快路径);
3. 否则退化为**"这段文本仍逐字存在于当前正文"** → 有效(容忍切块边界重排)。

6 项离线测试(`tests/test_chunk_vector_compat.py`)覆盖:改稿仍拒、重切仍留、
文本已不存在仍拒、`seq` 类型异常不崩。

**运维补口**:新增 `scripts/ops/rechunk_project.py` 与 [RUNBOOK §10](/root/ai-write/docs/RUNBOOK.md):

```bash
cd backend
python -m scripts.ops.rechunk_project --project-id <uuid> --dry-run   # 先看章数
python -m scripts.ops.rechunk_project --project-id <uuid>             # 幂等重建
```

容错只是防事故;要拿到"干净的叙事单位",切块算法改过之后仍应重建一次。

## 3. 双盲 A/B 评审工具(`arm_judge`)

用来回答"把 `SCENE_LENGTH_MIN_RATIO` 从 0.85 抬到 0.95,到底是变好还是只是变长"。

```bash
cd backend
python -m scripts.quality_eval.arm_judge \
  --a ../docs/evaluation/longrun-100-20261117 \
  --b ../docs/evaluation/longrun-100-095-20261117 \
  --out ../docs/evaluation/ab-095-20261117 \
  --sample 20 --judges deepseek-chat,claude-sonnet-4-6 --seed 17
```

- 同一章号的两份文本,逐 (章, 评审) 用 `sha256(seed|章号|评审名)` 决定谁当"文稿一",
  **提示词里只有文稿一/文稿二,没有 A/B、没有参数名**;解盲映射只写进 `verdicts.json`。
- 评审返回 `{"preference":"1"|"2"|"tie","reason":...,"evidence":...}`;解析复用
  `judge._loads_lenient`(模型把对白引号写坏也能救);单条失败计 `skipped`,不整批崩。
- 产物:`verdicts.json`(逐对判定 + `arm_1` 解盲)、`summary.json`(胜率/平局率/
  两评审一致率)、`REVIEW.md`(中文表 + 分歧最多 3 章的理由原文)。
- 调用量 = 章对数 × 评审数(20 × 2 = **40 次**);`--dry-run` 零调用。
- 21 项离线测试(含"提示词不泄漏臂信息""同 seed 可复现""坏 JSON 仍能取到偏好")。
