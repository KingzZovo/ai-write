## 已确认并修复的问题

- 分流评审一路失败、缺少issues、坏条目及无法解析的响应会变成空问题；检查器异常还会获得5分和整体通过。
- 多候选首稿评审异常被换成空对象，成为“零问题”优胜者；改写预算耗尽后即使仍有硬伤也会进入done。
- 二元一致性复核实际输出`is_issue/severity/reason`，旧调用却按issues数组消费。现在逐条核查，否定结论保留审计记录并移出问题计数，复核不可用明确标记。
- 手动面板读取`checker_name`，API返回`name`，明细可能消失；面板自行平均分数，缺项与失败不能可靠显示；切章后旧响应可能覆盖新章结果。
- 没重提地点、正文重复“不能飞行”、冷酷人物说笑/老练人物害怕被机械判错。旧位置/死亡重复扫描退出自动判错，已有ContextPack负责来源材料；关键词观察与具体问题分开。
- 冻结复核进一步复现了失败阶段恢复沿用旧评审、截断稿在通知失败后被重新评审放行、旧finalize正文覆盖当前稿、必需流被not_applicable跳过，以及JSON指数溢出漏检，现均已修复。界面证据原句完整换行显示。
- 所有候选评审失败后，原恢复路径只检查第一稿；现重新核对全组已保存稿。恢复只更新相同正文的报告并保留ID和作者选择，不重复生成或插入；候选内容不一致时停止，旧报告历史仍可查。

## 完成与待审的合同

`review_contract`要求正常结束的完整JSON，拒绝截断、未知结束、重复JSON键、修补出的部分数组和非有限数字。hard/soft发现必须附本稿能逐字找到的短引。SHA-256、完整流集合和问题计数在排名/改写/完成前重新检查；旧报告和不一致回执不能当作完整评审。

这些校验只证明响应结构与引用位置，不证明观点正确。模型仍可能误解因果、人物和留白，所有自动结果都标为`needs_author_review`。正文是否合格继续按[中文作者/编辑标准](CHINESE_FICTION_EDITORIAL_STANDARD.md)审读。

| 情况 | 自动行为 |
|---|---|
| 评审缺失、不完整或对应别稿 | 停在needs_review，保留所有已交付候选 |
| 完整评审有硬伤且还有预算 | 带当前完整候选和新核对材料进入改写 |
| 硬伤仍在且预算用完 | 待审，不能进入finalize/compaction |
| 有需作者处理的soft问题 | 待审，自动分数不覆盖这些发现 |
| 完整评审未报告hard/soft | 自动流程可结束，文学状态仍需作者审读 |
| 正文/修订明确截断或结束未知 | 保留已收到内容与旧稿历史，不能靠重新评审把片段认证成完整章 |

BVSR只对完整本稿评审按`hard_count, soft_count`排序。数字score保留为兼容诊断，不含词表罚分，不作文学评分；不可用候选score为null。每稿在评审前单独checkpoint，发生来源或写库故障时仍能从GET generation-run的checkpoint查看已保存稿。正常收集结束后所有稿进入chapter_variants；API明确返回各稿review_status。作者仍可显式选用未审稿，保留selected_by_user。

恢复使用已交付内容，不清零改写预算；rewrite/finalize及全组评审失败都重新核对当前材料，不能把上次材料当本次来源证明。即使重启后BVSR配置关闭，已开始的候选组仍按原候选数继续。报告更新前短事务锁定相同运行的候选、核对正文，并保留作者已选稿；选择截断稿仍为待审。失败事务先rollback，再读取运行记录并保存终止原因。

既有并发resume互斥尚未在本批增加，也未证明多个worker同时执行同一run的安全性。旧variants接口直接应用正文还缺少作者当前正文的版本条件，需下一批单独治理；本批的候选报告行锁不能替代这些保护。

后续进展：候选正文应用已在[候选应用报告](variant-application-20261008.md)对应批次补齐版本比较、旧稿备份、原子提交和共同章节父锁；旧generation-run执行互斥仍待完成。

独立裸Prompt的`POST /api/bvsr/generate`没有对应实现且缺章节来源，现明确返回410并指向作品/章节生成运行器；这不是新增的独立生成服务。实际支持的BVSR仍沿用已有启用配置及generation-runs、variants接口。
