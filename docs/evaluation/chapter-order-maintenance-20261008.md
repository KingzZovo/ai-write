# 章节顺序维护（2026-10-08）

源码实现与离线验证完成，未部署。本轮无新迁移，累计迁移head仍为`a1001943`，尚未应用到运行数据库。最后核实的隔离运行版本仍为`c4b4a4b`。

## 已核实问题

`OutlineTree.moveChapter`通过两次PUT交换章号，第一次成功而第二次失败时留下重复章号。`Chapter`插入监听器与章节PUT以“前卷章数＋本卷章号”生成全书位置；此前卷插章/删章、卷重排不维护其他章节，稀疏卷内章号也可能产生重复或倒序。来源核实会因此排除记忆，不能靠换模型解决。

## 已实现

1. 建立共享的顺序写入服务，短事务内复用生成互斥、资料物化锁和项目锁。严格拒绝不明确的卷/章编号，不猜历史伏笔号。按当前卷序、章序维护完整作品的持久化全书位置，读取和更新只涉及轻量元数据。
2. 章节新增、删除、调整到空闲章号，以及分卷创建/删除/调整、卷纲生成/重新生成、弧创建与异步书纲创建空卷接入维护。移动和重编号只改位置与版本，正文和章节ID不变；显式删除、重新生成沿用各自原有流程。来源位置变化通过现有数据库通知及读时来源核实处理。
3. 新增一次请求内完成的相邻章节交换，提交前比较两章的来源版本及邻接关系。旧两次PUT到已占用章号的方式明确拒绝。界面读取服务端保存的全书位置，移动失败先刷新核对，不盲目重复交换。
4. 新章节在当前事务内使用临时位置，整书重编号成功后才提交，避免每章重复执行旧计数查询。旧ORM插入监听器仅保留给直接ORM调用者兼容；正式业务写入不依赖它完成顺序维护。
5. 章节列表返回`global_idx`和`order_version`；轻量读取在SQL中排除`content_text`。重编号每批最多200章，只改有变化的位置。移动版本时间严格递增，系统时钟回退、移动后再移回也不能让旧请求重新生效。
6. 暂停后的整书任务恢复前核对当前章节ID集合和任务原清单；新增/删除/替换导致清单变化时要求新建任务，避免漏章后误报完成。单纯移动仍能按当前顺序执行，进度面板显示当前章号。卷重新生成保存稳定`volume_id`，避免仅靠旧卷号定位。

## API与作者操作

`POST /api/projects/{project_id}/chapters/{chapter_id}/move`接收`neighbor_id`、`expected_version`、`expected_neighbor_version`；两章必须属于本书同卷且相邻，版本一致才在单个事务交换。30秒内未确认提交则不返回成功，先刷新检查实际顺序；客户端不会盲目重发交换。

通用章节PUT仍可调整到空闲的正整数字号。已占用的章号返回409，旧的“两次PUT交换”明确停止；界面上移/下移使用新入口。创建和更新的卷/章号拒绝0、负数、布尔、浮点和字符串隐式转换。
