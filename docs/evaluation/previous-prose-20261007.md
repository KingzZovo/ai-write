# 邻章当前原文进入续写上下文

## 实际问题与修复

上一轮第二章实际 writer 提示只收到第一章“摘要缺失或与当前稿件不匹配；须核对正文”，没有旧句，也没有作者修订后的新句。该章主要由作者重复提供的细节支撑，不能据此认定自动衔接已经可靠。

ContextPack 增加独立的紧邻前章当前正文块。读取仍按同项目、跨卷顺序定位前章；过去最多五行的 SQL 窗口中，每行只传最多 3500 字符的结尾和原文长度，避免载入整本或完整长章。用于呈现的仅紧邻一章，短章提供全文，长章优先保留窗口内完整后续段落并标注前部省略；整段超过窗口时如实标注可能从句中开始，不把残句当完整事实。

正文、状态和章号用同次 SQL 读取的标量值，避免借用会话里旧 ORM 对象将作者新草稿标成 completed。草稿明确标为待审参考；空章不跳过，重复章号不任取一份正文。失效摘要继续被排除。

新增原文块在最终预算分配中为 required：可用预算不足时清楚报错，不能静默删去或截断整个必要块。3500 字符是数据库读取窗口，不是对小说篇幅、句式或写作风格的限制；长章更早的信息仍依赖经验证摘要及其他来源，不能宣称这能覆盖全章所有细节。

## 验证与独立复核

83 项针对性测试通过（11.01 秒），新增 8 项真实 PG/预算测试：完成稿和待审稿在改稿、摘要失效后进入最终 system prompt；长前章读取有界；前章空白、重复、移出本项目不任取错误来源；低预算明确拒绝；旧 ORM 状态不影响新正文标签。首次新测试夹具漏填必填章名，补齐后通过。

按 shadow-mind 无可信只读隔离环境的回退条款，本地冻结代码做两轮复核：正确性核对 SQL 项目/先后边界、非 ORM 状态快照、空白和重复处理；完成度核对原文块真正进入 to_system_prompt 的必要预算，而不只存到中间对象。复核发现并修正了复用旧 ORM 状态的风险。全量 1978 passed、4 条既有 warnings（310.90 秒）。ARM 四个隔离服务已更新至 636b233/a1001930，各 233 个 Python 源文件逐项一致，API 健康；生产未更新。

## 实际结果

SSE 在 98.233 秒到达 `[DONE]`，保存 1413 字符。场景规划、逻辑检查、摘要使用 CPA `gemini-3.1-pro` 别名；场景写作临时使用 `gpt-6-luna` 别名。别名不证明上游身份，不据本例替换默认。运行后 scene_writer 原 endpoint/model/tier 已恢复。

实际 scene_writer 日志解码 messages_json 后核验：包含 `【紧邻前章当前正文】` 和“沈青把用完的笔和橡皮收进文具袋里，拉上拉链。”；不包含原错误句“沈青把清单折好，放进自己的工作本里。”及故意留下的旧摘要。第一次诊断脚本未解码 PG JSON 字符串，错误显示所有中文均未命中；修正脚本并检查实际 messages 后得到上述结果。该误判发生在诊断脚本，不是产品上下文。

正文恢复八点预约、六本台账，陈川和站长次日核对封存，消息通过短信抵达沈青，没有切换到她不在场的车站。旧清单错误没有复现，但新章没有实际动用清单，不能据此证明它在更复杂后续场面中一定保持位置。此样例证明当前原文确实到达写作请求，不证明长章窗口之前的信息已全覆盖，也不是 Gemini/Luna 公平对照试验。

### 编辑式审读：仍需局部修订

知道模型路线的 Codex 审读，无真人盲评。与中文小说参照一致，关注人物反应、场面详略和自然收束，不用分数决定文学合格。

- 父亲从“别再翻了”到“你不是也要等消息吗”，能看出他注意到女儿的不安，父女有实际回应；复诊、同事履约、早餐谈工作均有结局。
- “又检查了一遍……自己去确认预约信息……去问问还要不要补什么手续”连续写确认；作为人物谨慎的表现可以成立，但后续“按流程办完后续手续，复诊便算结束”又变成办事概述，语言偏泛。
- “昨晚交到陈川手里的钥匙，已经在站长到场后用于开柜”是从短信完成结果推想的正常办理过程，不能硬判为必然视角违规；不过接在短信复述后又细述一次台账与封存，使场面重复。可把重点留给她终于收起手机的动作。
- 最后一段“复诊已经结束，车站那边的交接也有了结果；至于停运之后的日子，她暂时还没有答案”再次概括读者刚读过的三件事，削弱早餐对话的余味。可保留吃完早点一起回去的行动收束，不必再解释主题。
- 开头布袋系袋口，后来拉拉链并非必然矛盾（袋子可以同时有两者），不制造硬伤；是否简化交由语言修订，不能据此触发强制重写。

未为本例增设词频、对话或段落配额；没有将上述文学意见冒充通用正则规则。
