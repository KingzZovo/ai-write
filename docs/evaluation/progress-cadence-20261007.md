# 异步进度提交频率修复（2026-10-07）

《修补以后》整书大纲实测中，三个模型阶段已返回，任务仍缓慢消费片段。旧代码每 5 个片段做一次数据库提交；当模型逐字或以很小片段返回时，数据库往返成为主要开销。不能据此把整段等待时间全部归因于模型速度。

## 修复

`generation_tasks._ProgressWriter` 按单个任务持有时钟，首次进度立即提交，此后距上次成功提交完成至少 2 秒才重新拼接并写入进度。整书、分卷和场景正文三个原有分支共用该策略。最终保存、错误保留和显式阶段切换不经过节流；没有引入后台写任务或并发共用数据库会话。

## 验证

- 针对性测试 22 passed：包括 1000 个微小片段、慢提交、不同任务独立时钟及提交异常。
- 全量后端：1999 passed，4 项既有 warnings，316.18 秒。
- 真实 PostgreSQL 临时表对比，同样 100 字且最终内容一致：旧方式 21 次提交/10.125 秒；新方式 2 次提交/1.054 秒。只验证数据库提交开销，不作为完整模型生成提速比例。
- 按 shadow-mind 进行本地独立复核：逐一检查三个调用点、终态写入、失败文本来源和时钟更新位置；未发现新增阻断问题。平台没有可信的子代理只读隔离，采用技能允许的本地复核。

## 边界与后续

整书原任务仍在旧镜像运行，没有重启、重复提交或切换该 worker。本次代码尚未装入隔离运行镜像；需待任务结束后再部署并复测。生产未更新。

间隔策略在收到片段时触发，不承诺模型停顿时每 2 秒刷新；进程被强制终止仍可能丢失尚未持久化的进度片段。最终正常保存不受节流影响。既有 broad exception salvage 可能把部分大纲标为 completed，属于下一项独立修复，不能因本轮测试通过而视为解决。
