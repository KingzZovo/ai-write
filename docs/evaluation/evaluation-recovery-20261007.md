# 评审任务中断恢复

任务已写入但首次消息投递失败，或 worker 中断后停留 running 时，启动去重会返回原任务。新增周期恢复，避免只能反复看到同一停滞状态。

## 实现

- `backend/app/services/evaluation_recovery.py`：扫描超过60秒未更新的 pending/running，默认20项、最大100项，pending优先；与worker共用任务会话锁，在绑定连接内重读状态、核对更新时间、提交本次投递时间。
- 释放锁后投递原任务ID；完成、失败、删除、其他恢复器刚更新的任务不再投递，活跃worker锁忙时跳过。提交失败不发消息，投递失败保留原任务，下个窗口重试。
- `backend/app/tasks/evaluation_tasks.py` 注册 `evaluations.recover_pending`；Beat每60秒执行，周期消息60秒过期。恢复器本身不调用模型。
- 共用300秒协作式批次预算，单次投递等待10秒；取消传播。统计返回 examined/enqueued/busy/skipped/failed。

## 验证与复核

41项相关离线测试通过（恢复、worker锁、上下文、启动去重、批次期限）。新增真实PG测试已成功收集1项，覆盖持锁时不投递、释放后原ID投递及重复扫描；未执行，不能作为真实数据库验收。

按照shadow-mind做本地两轮复核：并发/持久化检查确认锁内复核、提交先于发布及终态保护；完成度检查确认只是消息恢复，不声称正文质量或部署完成。当前平台无可靠只读子代理隔离，未启动子代理。

投递适配器最初使用真实线程的测试在输出测试进度后停滞，两轮均已中止；最终改用线程替身，验证原ID与caller参数，41项正常退出。真实线程/消息队列路径尚待运行环境验证。

## 剩余风险

线程等待超时不能终止底层同步发布，可能晚到；worker互斥与完成态检查保护重复消息，但模型结束后、落库前崩溃仍可能再次调用模型，不保证外部费用恰好一次。活跃running条目可占据批次，pending优先也可能推迟running恢复；需要规模测试、恢复索引与公平调度进一步验证。Beat/worker必须正常运行才有周期恢复，60秒不是恢复时限承诺。
