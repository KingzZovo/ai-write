# 人物状态进入写作上下文的完整性修复

2026-10-08。基于 `96612f9`，本轮只修改本地源码和文档。没有访问运行服务、执行真实迁移、部署或调用CPA模型。

## 确认的问题与范围

正文实体抽取允许任意有效JSON状态字段，`verified_character_states`也会按来源保留各字段，但旧角色卡只使用位置、实力、心理几个属性。伤势、身份、资源、装备等信息虽已保存，却可能不进入写作的必需上下文；同时存在“状态”和“情绪”时，一般状态会被漏掉。只有“状态”时，它又会被误标为心理。

另外，旧字段选择按键名优先。例如较早的`mental_state=焦虑`会压过后章的`情绪=释然`。状态读取异常原先只记日志，随后仍可用旧档案继续生成。

本轮先以真实SQLite查询、正文来源回执校验、实际状态覆盖和最终Prompt渲染复现以上四项，四项均先失败。未将没有运行入口的旧`outline_to_facts` ETL当作当前生成链修改。

## 最终行为

- `services/character_context.py`统一维护`CharacterCard`，原`context_pack.CharacterCard`导入方式保留。PG和已核对来源的图谱状态使用同一组装逻辑。
- 每个状态字段保留自己的章节ID、来源摘要和全书章号。Prompt按实际来源分组；不会把早章留下的伤势重新归到后章的情绪记录上。
- 完整保留JSON字符串、数字、布尔、数组、对象、空集合及`null`。一般“状态”不再作为心理的备用名称；静态档案中的位置、实力和心理标为档案参考。
- 相同字段按来源章选择较晚值；已有支持的中英文属性名用于快捷属性取值时也比较章号。Prompt保留不同字段名及来源，不猜测任意语义同义关系。
- 专门的位置记录保留来源时间。较晚状态中的位置可以覆盖早章位置，同章以专门位置记录为准；不同值不会仅因来源回执相同而被去重。由状态产生的位置快捷值变成`null`时同步清空，避免旧值残留。
- 图谱补充先在副本上组装，异常不会留下半份修改。必需的位置、状态和认知读取失败明确中止；合法的空历史仍允许继续。
- 人物卡继续作为不可拆分的必需预算块。空间不足时明确报预算不足，不用只留名字或截断字段的方式伪装上下文完整。
- 移除认知节选外层的“只能依据知道列表行动”旧提示，保留有时间的认知记录语义；未记录某项不等于人物不知道，早章未知不能压过后章明确获知。

`ChapterGenerator`通过`pack.to_messages()`使用以上内容；`SceneOrchestrator`的规划和写作背景使用`pack.to_system_prompt()`。这不是只改变测试展示的独立渲染器。

## 固定输入与中文小说验收意义

下面是测试状态输入，未调用模型，不是新生成的中文样章：

```text
CH-900：伤势=左手骨折；身份=停职巡检；资源={银两:0, 凭据:[]}；情绪=镇定
CH-901：情绪=略安
```

旧角色卡只能看到心理“略安”。现在必需上下文包含CH-900的伤势、身份及资源，CH-901的情绪另列，早章“镇定”不作为同名字段的当前值再次出现。

按[中文作者/编辑标准](CHINESE_FICTION_EDITORIAL_STANDARD.md)，后续正文应让动作受伤势制约，让付费或交换行为体现人物实际可用的资源，并承接人物在前场形成的情绪。不能用“平静”抹去“重伤”，也不能把“重伤”自动解释成惊恐。正文无需逐段复述这些记录；人物有可信行动、场面完成关键转折，才有文学上的连贯性。

本轮测试只能证明这些材料不再被工程组装丢失。来源回执核对不证明模型对原文的理解正确，也不能代替正文审读。
