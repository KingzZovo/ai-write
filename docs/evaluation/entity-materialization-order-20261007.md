# 资料投影的项目互斥与提交结果

状态：实现与离线回归完成，真实 PostgreSQL/Neo4j 验收和部署未完成。

## 问题与修改

原 materializer 先读取图快照，再创建 PostgreSQL 写事务。不同入口可同时读取不同时间的快照，然后以相反顺序提交，旧快照可能覆盖已经完成的新投影。章节实体 worker 的项目锁没有覆盖作者编辑、书纲导入等所有调用。

- 公共 `_materialize_entities_to_postgres` 统一先打开写会话，并通过 `entity_materialization_lock` 获取项目级 `pg_try_advisory_xact_lock`，之后才进入图快照读取。
- 图读取、资料写入、最终提交由同一个 PostgreSQL 会话保护。事务提交/回滚/会话关闭释放锁，不使用单独的可失效租约连接，也不在获得锁后提前提交。
- 锁命名空间与章节实体 worker、production 项目锁分离，避免现有调用持有其他连接锁时重入。同项目忙时立即抛出 `MaterializationBusy`，不等待持有作者行锁的另一个任务，不提前抓取快照。
- FastAPI 注册该异常为 503 + `Retry-After: 2`，给旧资料编辑入口明确的可重试响应。作者人物保存原有 503 路径继续保留草稿；持久化书纲/章节提取可按原恢复机制重试。
- 原执行体提取为内部 `_materialize_entity_snapshot(db, ...)`；写入逻辑主要做一次缩进调整，可用 `git diff -w` 核查实际语义变化。
- 修复既有提交失败吞错：即使 strict=False，提交失败也必须进入失败计数分支，不能继续报告刚才计划写入的数量和 success 指标。strict=True 继续向恢复入口抛错。
