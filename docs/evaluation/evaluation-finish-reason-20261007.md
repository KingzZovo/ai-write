# 评审拒收明确未正常结束的响应

## 问题与修改

路由保留结束原因后，ChapterEvaluator此前仍直接解析result.text。即使供应商明确报告length/max_tokens，只要JSON刚好可解析（或可修复），就可能产生有效高分/低分，进而影响通过与自动改写。

现于解析之前检查结束原因，明确非正常结束返回_failed_evaluation('incomplete_response')，保留system维度失败记录，parse_failed=True。正常stop/end_turn/stop_sequence和旧端点无元数据仍进入原有严格JSON校验。不会因响应不完整自动重试模型或生成文学结论。

流式进度和EvaluationPanel新增中文原因显示；评审面板继续隐藏失败哨兵分数。存储仍使用既有issues_json中的failure_reason，最新评审接口现有重建逻辑可以保留该原因，不需要迁移。

## 边界

供应商无结束原因时仍兼容，不能称已验证完整。正常结束和有效JSON也不证明评审判断正确，更不能代替中文作者式审读。本批没有新的真实CPA/Gemini调用、数据库故障/持久化、浏览器整流程或部署验收。

默认定点改写、显式整章改写、长篇事实来源及文学质量仍需按总计划继续验证；此处只消除已知不完整响应被采纳为评分的路径。
