# 作者人物档案的持久同步恢复

状态：代码和离线验证完成，真实数据库故障注入、浏览器状态恢复及部署待完成。

## 修改

之前作者保存图档案后，若 PG 同步繁忙、提交失败或进程退出，只能靠再次点击同步。本轮把待办和档案写入同一个 Neo4j 事务：

- 每次通过条件比较的保存同时写入新的 `profile_sync_token`、到期时间和尝试次数。图提交成功后，待办不会依赖 HTTP 请求或 worker 内存存活。
- API 严格同步 PG 成功后才确认该 token；确认失败同样保留可重放待办，返回 503，不声明已完成。
- 新增 `character_profile_recovery` 和每分钟执行的 `entities.replay_author_profiles`。每批最多选取 20 个到期人物，按项目合并调用公共 materializer；不改写人物档案、不调用模型。
- 恢复成功只清除本批 token。清除和失败退避都先取得人物节点写锁，再比较 token，避免旧任务等待锁后误清除/推迟新作者稿的待办。
- 失败按 1、2、4、8、16、32、60 分钟上限退避；每项目同步最多 120 秒，失败后的退避写入最多 15 秒。取消不转成成功，不删除 pending token。
- 确认返回丢失可重复投影；同项目已有公共 PG 事务锁保护，成功完成的旧投影不会再越过新投影提交。

Neo4j 动态属性无需 PostgreSQL 迁移。恢复能力需部署 API 与 worker/beat 后才生效；本轮未部署。

## 本地独立复核

依 shadow-mind 的无可靠只读隔离回退，分别复核数据持久性/竞争和任务入口/验收。检查发现仅在 Cypher WHERE 比较 token 后直接 REMOVE 不足以表达锁后复核，已改为依赖原值的写锁操作在前、token 比较在后；退避同样处理。同步 token 返回值改变后，已调整真实并发用例的成功结果断言。
