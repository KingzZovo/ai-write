# 移动端手工编辑保存与旧稿冲突保护

## 实际问题

390×844 Chromium 打开隔离项目、选择“早班”。等待 1413 字正文真正加载后输入新句，观察无章节 PUT，刷新后编辑丢失。源码只有 textarea 的本地 setEditorContent，没有保存入口。第一次浏览器诊断没有等正文返回，读到 0 字，已修正等待条件再复现，不把空编辑框的结果当证据。

## 改动

移动端提供“保存正文”和加载/未保存/保存中状态。保存发送当前稿、加载时原稿 expected_content_text 和 needs_review；成功更新章节列表及编辑基线，失败保留本地稿。大幅删改仍遵守原后端保护，不能静默 force。模型故障/网络异常用安全中文提示，冲突信息说明服务端新稿未被覆盖。

保存、加载或生成时禁止编辑和再次保存；未保存时不能直接生成覆盖正文。切章和返回项目列表对未保存修改进行明确确认，刷新/关闭窗口有 beforeunload 提醒。加载失败保持不可编辑，不能把空框当原稿；用请求序号排除迟到章节加载/保存回调，切章不显示旧章内容。此处不宣称已覆盖应用所有导航入口或提供离线持久化草稿。

章节 PUT 新增可选 expected_content_text。带此条件时按项目归属取得行锁，并以数据库当前正文逐字比较；不符返回 409，且在标题、状态、正文任何修改前拒绝，force 不能绕过。条件为空字符串仍有效；旧客户端不传该字段时保持现有行为，因此不是全站所有保存入口均已具有并发保护。没有迁移。

## 测试与复核

11 项后端针对性通过（5.21 秒），新增真实 PG 验证旧稿不能连带改标题/验收状态，以及两个同基线并发保存只能一个成功、另一个 409。

前端新增 4 项组件测试：加载基线随保存传入、成功后待审；冲突保留本地稿且取消切章不丢稿；加载失败不可编辑/保存；旧章节迟到响应不覆盖新章。全量前端 111 项、TypeScript 和生产构建通过。首次 mock 将 /api/projects 返回成数组而非实际 {projects:[]}, 修正夹具后通过。

按 shadow-mind 的无可信只读隔离回退条款，本地完成正确性与数据安全复核：条件比较发生在同一行锁内、失败前不改字段；加载失败必须独立标记，不从 textarea 是否为空推断已加载；保存回调匹配当前章节请求序号。复核补充 chapterLoaded 独立状态，避免缓存中的旧正文使加载失败空框被误判为可保存编辑。后端全量 1997 passed、4 条既有 warnings（316.09 秒）。
