# 旧 Run 模型阶段记账与中断预算

2026-10-09，分支 `fix/2026-10-06-pipeline-safety`。本批完成源码与离线验证，未部署。

旧运行器此前在模型返回后才增加改写次数，取消或断线会漏记预算；初稿也可通过反复恢复无限重试。现在每次逻辑模型阶段先保存尝试记录，改写同时消耗原预算，确认提交后才调用模型。恢复保留已消耗的次数与原候选数量。

## 实现与行为

- 新 Run 与固定请求一起创建版本 1 的 `checkpoint_data.attempt_journal`，绑定 Run、作品、章节、原改写上限、多候选开关和数量。没有在旧 Run 恢复时补造历史。
- 初稿、额外候选、候选评审、主评审和改写分别记录 UUID、阶段及位置、顺序、开始/结束时间、输入摘要、交付前摘要和结果摘要。评审行 ID 与调用记录 UUID 对应。
- 初稿、每个额外候选、每个候选评审及每轮主评审分别最多 3 次；已返回的不完整评审同样占用次数。改写按原请求的 0–8 次上限预占，中断不退款。最大配置下整个 Run 至多 83 个逻辑阶段尝试，**不是整次 Run 只允许 3 次**。
- `rewrite_count` 在新版协议中表示已消耗的改写尝试数，包含未确认输出的调用。上限为 2 时，第一次中断后先重新审查原稿，最多再改写一次；上限为 1 时不会再改写。
- 模型阶段前的记录和改写次数在同一事务提交，提交未确认就停止调用。模型返回后，交付记录、正文检查点或评审报告一起提交；评审服务不再先单独提交报告。
- 显式恢复仍先取得作品物理锁，核对原请求、完整章稿/分卷来源及原预算。未确认调用先核对交付前摘要、没有匹配回执的评审行及目标候选记录；没有交付证据且来源一致才允许继续。旧 UUID 留在历史里，新尝试使用新 UUID。
- 有无法解释的已存交付时保留并待审，不自动覆盖。所有未确认阶段都会检查孤立评审，初稿和额外候选也不会漏掉已存评审。来源已变化仍由原提交合同拒绝执行，保留原状态。
- 候选评审恢复时继续核对全部候选，但新报告提交前保留上一份报告；预算或来源失败不会先清空作者可查看的旧报告。既有候选 ID、作者选择与正文应用合同保持有效。
- 严格校验版本、身份、类型、UUID 唯一性、阶段位置、次数、日期、摘要及改写计数。缺历史或坏记录不能清零重建。旧任务若连原请求/来源证明也缺失，仍先由原来源合同拒绝。
- `generation_run_views` 共用安全的状态投影：嵌套坏字段原样保留，整个检查点无法解析时放入 `unparsed_checkpoint` 供查看。读取和待审响应不会因为这类结构损坏返回 500；投影不会证明原记录有效。
- 普通重复 POST 继续只读原请求，只有明确的 resume 才核查未确认调用。本批没有新增自动恢复入口或前端调用方。

| 待审原因 | 含义 |
| --- | --- |
| `model_call_history_unverified` | 原调用历史缺失、损坏或与检查点不符 |
| `model_call_delivery_unverified` | 未确认调用已有无法对应的交付，须先检查保存内容 |
| `model_call_budget_exhausted` | 当前阶段的原次数已耗尽 |

这里记录的是**逻辑模型阶段**，一个阶段可能含工具调用、上下文准备或多个有界评审/Provider 尝试；不能据此承诺每个 HTTP 模型请求恰好一次。保守预占可能包含“模型尚未真正执行、提交确认已丢失”的尝试。输入摘要也不是全部上下文、Prompt、路由或模型版本的冻结副本，每轮仍准备当前材料。

## 容量、协议与回滚

1005 章、超过 500 万字符的 SQLite 书库中，恢复核查只读取目标章正文一次，没有读取另外 1004 章正文。候选/孤立评审核查只查本 Run 的元信息，不加载候选全文；历史长度受原请求预算约束。

本批没有新增数据库列或迁移。`attempt_journal` 使用已有 JSON 检查点；模型注释明确了新版 `rewrite_count` 语义。AST 检查确认源码单一迁移头仍为 `a1001956`，累计迁移尚未在真实 PG 应用。

发布须让全部旧 Run 写入者使用同一协议。回滚前应停止执行并保留新协议记录；旧版本不能继续恢复带 journal 的 Run，否则会重新绕过本批阶段上限。不能通过删除 journal、清零次数或重置请求来适配旧版本。已完成的旧 Run 仍可只读。
