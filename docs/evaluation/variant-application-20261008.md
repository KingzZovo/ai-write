# 候选应用的正文版本与事务保护

2026-10-08，承接评审完整性提交 `7289188`。本批未部署，未调用真实服务或CPA；没有新增迁移，累计源码头a1001950仍未在真实PG执行。

## 修复的问题

旧`POST /api/variants/{id}/select`默认直接替换正文，没有比较作者看到的保存稿，绕过普通编辑的空稿/骤缩保护，也未备份被替换的正文。候选的旧word_count还会覆盖实际字数。提交或确认失败时，接口可能留下不明确的500结果。

现在应用候选必须提交`expected_content_text`，在写锁内逐字比较当前保存稿。普通编辑与应用候选共同使用`chapter_content.check_chapter_replacement`：版本不同一律冲突，`force=true`只允许明确的清空/缩短，不跳过版本校验。已有200字以上正文不能被默认清空；已有1000字以上正文不能被默认缩短超过60%。这些沿用既有防误删规则，不是小说质量标准。

真正替换前，将完整旧稿保存到`chapter_versions`，来源为`variant_apply_backup`，同时记录候选ID、运行ID、原章名/状态以及前后正文摘要。旧稿版本、正文和作者选择同事务提交；同文应用不新增备份、不重复派发抽取。字数按真正写入的正文重新计算。

## 接口合同

应用请求示意（占位文本须替换为作者核对过的完整保存稿）：

```json
{
  "apply_to_chapter": true,
  "expected_content_text": "作者核对过的当前保存稿全文",
  "force": false
}
```

`apply_to_chapter=false`只记录作者选择，不替换正文，也不要求正文前提。成功响应在既有候选信息之外返回`applied_to_chapter`与`backup_version_id`；只有提交获得确认后才返回成功。缺前提的旧默认请求现返回428，需要调用方先读取保存稿。这是有意收紧的接口合同。

| 情况 | HTTP与行为 |
|---|---|
| 未带当前保存稿 | 428，正文和选择均不改变 |
| 保存稿已更新，即使force=true | 409 `chapter_edit_conflict`，保留后来改稿 |
| 默认清空/大幅缩短 | 400，沿用普通编辑保护码 |
| 候选/章节不存在或作品在回收站 | 404，不应用正文 |
| 生成、章节调整或资料同步占用 | 409，请结束相关操作后重新核对 |
| 写库失败或提交确认不明 | 503 `variant_selection_unconfirmed`，不能直接认定已保存或未保存，应读取当前正文和选择核对 |

本批没有固定请求的幂等回执；成功提交但丢失回执后，重复原请求可能返回版本冲突。普通编辑接口仍保留原有可省略`expected_content_text`的兼容行为。本批未新增前端面板，当前前端源码未发现这一旧候选接口的调用方。

## 并发与来源

应用正文复用作品生成锁→资料物化锁→作品→章节→候选顺序，回收站和活动整书任务在锁内检查。正文和候选使用`populate_existing`重新读取，不能复用请求会话里的旧ORM对象。

第一次冻结复核发现应用单个候选、候选刷新及外键插入存在相反的锁顺序。现`persist_variants`、`select_variant`与应用正文都先锁所属章节，再处理候选行；父锁只读取ID，不加载其他候选的正文。这消除了本批识别的相反顺序，真实PG并发仍需实测。候选收集的模型调用在取得这些写锁之前完成。

成功提交后发送既有实体抽取通知，已保存变更的持久恢复仍依赖数据库outbox触发器；本批SQLite用例未执行这些PG触发器。新的候选写入行锁也不能代替旧generation-run的跨worker执行互斥。
