# 人物删除的原子性与可恢复清理

状态：实现和离线回归完成，数据库迁移、真实双库故障注入与部署未完成。

## 修复

原入口先删除人物状态，再单独删除人物；PG 清理异常被吞掉，既可能只删一半，也可能页面仍显示旧人物却返回成功。简单重放按姓名删除又会误伤后来重建的同名人物。

- 新增 `character_deletion`：同一图事务中核对原档案、删除独占状态及人物、写入 `CharacterDeletion` 待办。共享给其他人物的状态保留，重复状态边先去重。
- 删除请求必须携带 `expected_profile_json` 和 `deletion_token`。旧稿冲突拒绝；同项目同 token 记录保留，重复请求不再删除新建人物。删除前确保人物和删除请求的唯一约束；约束创建失败不继续删除。
- 新增 PG `AppliedCharacterDeletion` 与迁移 a1001932。以 `(token, project_id)` 记录已经提交的清理，不能因跨项目 token 相同相互干扰。
- 每个公共 materializer 在项目事务锁内先处理待删除记录，再建立当前图快照投影。清理 Character 及按名称保存的出场、认知、记忆卡；人物 ID 外键关联按既有 CASCADE 清理。
- 清理日志、旧资料删除、新图投影同 PG 事务提交，之后才确认图待办。若 PG 已提交但图确认丢失，重放根据日志跳过旧清理，不删除后来重建的新 PG 行。
- 新增每分钟删除恢复任务；失败只推迟本批选中的待办，避免失败项目持续占据队首。不调用模型，也不重新发送图删除。
- API 不吞同步失败，返回明确 `character_deletion_pending`。侧栏提交基线及重复请求编号，读回后才确认删除；后台清理期间只读取列表，不自动发出第二次删除，同名新行继续显示。
- 公共同步器的最终提交和成功指标上移到事务调用层，清理与投影一起成功后再记录成功，保留严格失败合同。

## 发布约束

必须先应用 a1001932，再成套发布 API、worker/beat、前端。仅带 name 的旧 DELETE 请求返回 422，不提供绕过旧稿核对的入口。图中的 completed 删除记录作为重复请求凭证保留，没有提前清理。

本轮未实际执行迁移或发布。静态迁移检查唯一 head 为 a1001932，不等于迁移已通过。
